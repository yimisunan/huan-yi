# 交流消耗与阶段结算讨论记录

性质：已确认设计方向，尚未实现；具体资源名称、基础量、等级差值、阈值与恢复规则未定。

用户说明：24体力/24小时仅来自其他游戏，不是本项目数值。为减少不同模型自由解释行动重要性的差异，希望每次发送有固定消耗；A/B/C选项可按等级扣除，自定义输入遵循同一等级边界，防止一句话包含无限或跳脱行动而无法界定。

讨论结论：

- 每条有效且正式接受的输入有固定基础消耗；网络失败、模型格式失败、读取不全及同request_id重交不重复扣除。基础消耗建议为交流额度，是否与时间/体力关联待定，不默认每句流逝一小时。
- 行动采用预定义等级和成本表；模型只在有限类别中提出分类及依据，不自行发明扣除数值，程序校验并查表计算。
- A/B/C是选项位置，不是等级。每条选项带稳定option_id、允许操作、等级和预期成本，玩家选择与自定义输入适用同一标准。
- 自定义输入基础消耗加行动消耗；多项行动需明确执行范围或拆分，不可全部按一次低档执行。分类不明、未支持或越界请求澄清，不凭高消耗购买必然成功或他人同意。
- 耗费资源不代表行动必然成功。已实际执行但结果失败可按规则消耗；未执行、请求被拒绝不收行动成本。
- 消息、实际事实和周期结算分开：接受后即保存消息与合法事实，不等阶段结束。阶段无新增重要事实时可记无新增事实，不为填存档制造事件。
- 额度阈值用于阶段整理，时间跨日/体力休息另行定义；上下文整理可发生在同一天，不能以模型上下文满了作为跳日理由。

设计局限：仅靠模型分类仍可能错分，必须有受限操作、前置条件与最大范围校验。程序能验证结构和已知条件，不能自动证明所有自然语言语义。下一份契约需要明确无法可靠归类时的处理路径。

授权边界：本轮记录和设计，不写入原存档、不启用扣费或资源消耗、不把候选数值当作项目事实。
