# 03 · 流式低延迟、下一句预取与时间戳字幕同步方案

## 一、现状瓶颈诊断

当前项目中：
- 后端 `语音运行.py` 与 `voice_client.js` **已经实现了** `stream: true` 分块流式转发和 `MediaSource (audio/mpeg)` 边下边播，且有并发去重缓存（`_cached_tts`）。
- 但主程序 `story_client.js` 的 `speak()` 仍然调用整段下载的 `VoiceClient.requestAudio()`，导致每次点按推进都要等整句音频完全合成并下载完毕才响第一声（长句通常等待 1.5~3.5 秒）。

---

## 二、方案 1：HTTP 流式首包即播 + 下一节点静默预取（低改造成本 · 立竿见影）

### 1. 启用 `VoiceClient.requestStream()`
在 `story_client.js` 播放 MP3 语音时优先尝试 `VoiceClient.requestStream()`：
- 当客户端支持 `MediaSource.isTypeSupported('audio/mpeg')` 且当前角色格式为 `mp3` 时，第一块 4KB 音频一到达（约 300~500ms）即触发 `audio.play()`。
- 若遇到 Android 老版本 WebView 不支持 MSE 或格式为 `opus`/`wav`，自动无缝降级回 `VoiceClient.requestAudio()`。

### 2. 有界单节点预取（Bounded Lookahead Prefetch）
在当前节点语音开始播放后，若本段 `history` 中已存在已展开或紧邻的下一条台词（注意：必须严格遵守后端隐私门禁，**绝不预取未揭晓的隐藏节点**，仅用于回看或已揭晓队列连播）：
- 使用独立通道 `channel: 'prefetch'`，限制字符 ≤ 280、单次 ≤ 2 MB，且利用后端 `_cached_tts` 去重缓存，切到下一句时 0ms 瞬播。

## 三、方案 2：SSE 时间戳流 + 逐字/逐句高光同步（官方新接口）

Fish Audio 官方现已提供 **`POST /v1/tts/stream/with-timestamp`**（返回 `text/event-stream`），在流式推送 `audio_base64` 的同时，实时推送 `alignment.segments` 词级时间轴：

```json
{
  "audio_base64": "T2dnUwAC...",
  "content": "那就留下来呀。有人陪着吃早饭，我也高兴。",
  "chunk_seq": 0,
  "chunk_audio_offset_sec": 0.0,
  "alignment": {
    "audio_duration": 3.42,
    "segments": [
      { "text": "那就", "start": 0.00, "end": 0.36 },
      { "text": "留下来呀", "start": 0.36, "end": 1.12 }
    ]
  }
}
```

### 最佳落地方案（安卓端文字同步演播）
1. **格式建议**：官方明确建议时间戳流使用 **`format: "opus"` + `sample_rate: 48000`**（Opus 帧边界干净，无 MP3 窗口重叠漂移，且流量比 MP3 128k 省约 60%）。
2. **后端桥接路由**（规划新增 `/api/tts/timestamps`）：转发请求至 `https://api.fish.audio/v1/tts/stream/with-timestamp`，按 SSE 事件透传给前端。
3. **前端卡拉 OK / 呼吸高亮**：监听 `<audio>` 的 `timeupdate` 或 `requestAnimationFrame`，根据 `currentTime` 匹配 `segment.start + chunk_audio_offset_sec`，让对话文字随角色开口节奏泛起柔和鎏金光晕（不遮挡阅读、支持 `prefers-reduced-motion` 自动关闭）。

### 参考 Python 代理片段（按需接入 `语音运行.py`）
```python
@app.route('/api/tts/timestamps', methods=['POST'])
def tts_with_timestamps():
    data = request.get_json(silent=True) or {}
    payload = _build_fish_payload(data['text'], data.get('voice_id', ''), data)
    payload['format'] = 'opus'
    payload['sample_rate'] = 48000
    headers = _fish_headers(data.get('tts_model'), 'opus')
    headers['Accept'] = 'text/event-stream'
    upstream = requests.post(
        f'{FISH_BASE_URL}/v1/tts/stream/with-timestamp',
        json=payload, headers=headers, stream=True, timeout=FISH_HTTP_TIMEOUT
    )
    def generate():
        try:
            for line in upstream.iter_lines(decode_unicode=True):
                if line:
                    yield line + '\n\n'
        finally:
            upstream.close()
    return Response(generate(), mimetype='text/event-stream')
```

## 四、方案 3：单次多角色戏剧合批（Multi-Speaker Dialogue）

`s2.1-pro`、`s2.1-pro-free`、`s2-pro` 与 `drama-3` 均原生支持单次请求内多角色无缝接戏：
- `reference_id`: 传入数组 `["旁白_id", "沈知韫_id", "苏婉青_id"]`
- `text`: 使用 `<|speaker:0|>`、`<|speaker:1|>`、`<|speaker:2|>` 标记换人

**适用场景**：
- 并非替代现有的「逐节点点按演播」（点按演播仍按单节点播放最佳）；
- 最适合在 **「剧情回溯（已读手记）」** 中提供 **「一键导出/连听本场广播剧」** 功能！把整场已读对白一次合成为自然气口衔接的完整有声剧 MP3，人物抢白与停顿浑然天成。

---

## 五、方案 4：WebSocket 实时流（`wss://api.fish.audio/v1/tts/live`）

若未来升级为流式边生成剧情边朗读，可通过原生 WebSocket `/v1/tts/live`（MessagePack 帧）在 LLM 输出第一个完整分句时立即推送 `TextEvent` + `FlushEvent`，实现真正意义上的实时声画同步。在当前 Pydroid3 + 完整 JSON 校验后再揭晓的架构下，优先采用 **方案 1（HTTP MSE 流式）** 与 **方案 2（SSE 时间戳）** 性价比最高、依赖最轻。
